01方案

不是 agent 自由探索，是一条由能力探针决定形态的三段式流水线。每一段的分工都是被实验逼出来的，不是设计出来的。

先探测，再决定证据怎么组织

这是整个框架最上游、也是唯一一个不能靠调参补救的决策。探针从部署读出图像与视频的 token 预算，策略随之改变：

部署图像预算视频通道帧的送法多加一帧的代价
gemma-4-31b280 token 硬上限70×32 = 2240video 通道—
qwen3.8-27b16.7M 像素原生无拼图延迟（实测慢 13×）
若走 gemma 的拼图路径280 共享—拼图分辨率
同一套 skill 换个模型必须走不同路径。“多给模型一些证据”在固定 token 预算的部署上等于“让每帧更小”——这是六轮失败的根源，也是探针现在会自动回答的问题。

三段式

① 定位 · CV，无模型

suspicion 六路信号在全帧率上算（不采样），成对时两条片段联合归一化，提名 k 处可疑区域。

信号只负责“往哪看”。让它直接判好坏，符号是反的——16.7%，低于随机：动得多的片段天然更可疑，而人评奖励动得多。

② 呈现 · 版式即约束

裁剪放大，相邻两帧一张图，每格 768px 源、有效 528px。版式由探针测出的 448px 可判读底线倒推。

8 列条带每帧只剩 264px，2×2 拼 384px，只有 1×2 并排过线。渲染层不是装饰，它决定细节能不能活到模型眼前。

③ 判定 · VLM，封闭问题

整体运动走 video 通道成对比较（带强制交换检查）；局部结构走逐处判定 normal/broken/unclear，判据统一到拓扑变没变。

开放式“哪段更好”一半判断经不起换边；“这一段有没有缺陷”55% 的对给出逐字相同答案。封闭问题它答得很好。
为什么输出天生是 point-wise 的

逐处判定是逐片独立的，结构上不可能有位置偏置；成对方向是分数之差的副产品，而不是反过来。这正是做 reward model 需要的形态——给一条从没和任何东西比较过的视频也能出分。

对 reward model 而言，seed 那一行是唯一要紧的

单策略的 RL / BoN 在推理时喂进来的是同一个模型的不同采样——就是 seed 族。跨模型对在那个场景下是 OOD 的。微调 RM 在那里 39.7%，低于随机；本方案 69.8%。

03为什么前六轮全部无效

不是方法不够好，是接口用错了。而这件事被一个固定的 token 预算掩盖了整整一天。

轮次做法结果事后判明的原因
18 / 16 / 32 帧扫描48–58%帧数涨，每帧像素跌（280 token 共享）
2逐片十项缺陷清单净贡献 0.055% 的对给出逐字相同答案
3加时间证据（差分条 + 曲线）−14 点差分条也是 16 帧采样，同一个盲区
4内容特征（骨长 / 对称 / 抖动）−6.3372 对拟合 33 维，过拟合
5放大到 448px + 逐处判定52.8–55.3%符号修正了，但召回太低
6k=3 → k=10 提高召回57.1% → 50.0%覆盖率翻倍，准确率掉到随机
7换 video 通道82.2% / 翻转 22%预算 8 倍，且唯一携带速率
前六轮的共同点：每一次“给模型更多东西”，都因为某个固定预算被稀释而失效。第七轮加的是独立的通道而不是同一次调用里的更多内容。
一个本该最先问的问题

运动质量主要是速率问题，而抽样恰恰是毁掉速率的那一步。清单模式里“卡顿 / 打滑 / 速度 / 幅度”四项在 1220 条片段上报出率是 0%——不是模型偷懒，是证据里根本没有答案。

教训已固化成探针：在优化怎么用一个接口之前，先确认用的是不是对的接口。

04被推翻的结论

全部来自本项目自己早先的报数。列在这里不是为了自省，是因为每一条都暴露了一类会重犯的错误。

原结论真相错误类型
加帧 +4.2 点，16 帧达 61.1%位置偏置。模型 74% 选 A 侧，人评基准 37%对照被静默跳过
point-wise 模型 66.1%口径错（弃权不进分母），实为 61.5%指标不合规
61.5% 是真实判别能力主要是生成器指纹。档位先验单独就有 82%缺平凡基线
逐处判定 k=3 得 57.1%样本增至 124 后掉到 50.0%小样本
seed 族是正确的评测靶子3–5 名标注员 64% 判平局，人自己分不开靶子不可分
爆冷集 83.9%n=31，CI [66%,100%]。稳健值是 64.1%（n=529）未标样本量
前两条与最后一条是同一个毛病的三种形态：一个数字不和它的 n、它的平凡基线放在一起，就没有意义。

05四个静默故障

共同点：不报错、照常出分、数字全假。它们比方法错误更危险，因为没有任何信号提示你去查。

交换检查被静默跳过参数缺省时提前返回，位置偏置冒充成 61.1% 的准确率
拿不到交换方式就返回 ok=False，跳不过去
200 条视频只写出 2 个文件渲染文件名描述的是视图而不是片段，6 个 worker 互相覆盖
内容寻址：文件名带图像字节哈希，碰撞即缓存命中
归一化删掉跨视频信息（咬了三次）200 条视频信号 p99 全等于 1.989；三条无关视频 loci 峰值全等于 3.784
加 raw=True；成对时两条片段联合归一化
线程爆炸在别人的作业里报错32 worker × 64 BLAS 线程打爆进程数，表现为另一个作业的解码失败
环境变量钉死线程数 + cv2.setNumThreads(1)
GPU 在客户端队列后面空转服务端 Running: 1 reqs、KV cache 1.3%，而并发 8 压测能到 1.62 req/s
CPU 预渲染走进程池，跑完再进线程池打 VLM

06未解决

  • S-S 与 M-S 仍是空白（51.8% / 52.1%）。同档不同模型的对，本方案和微调 RM 两边都接近随机。
  • 交换检查在 §1 口径下被惩罚（63.7% vs 强制表态 65.2%）。该口径不许弃权，被检出位置偏置的对必须硬猜，等于把“我不确定”变成随机。d==0 在官方函数、METRICS.md §1、trainer.py 三处有三种处理——对连续打分器无影响，对会弃权的判官有系统性影响。
  • seed 族的标注天花板。3–5 名标注员 64% 判平局，强偏好仅 7%（21 对）。要在这个切片上继续往上，需要新标注而不是新方法。
  • 两条路线应当合并。强弱分界线正好是“指纹有没有用”，这是合并有效的直接依据，不需要新数据即可验证。
