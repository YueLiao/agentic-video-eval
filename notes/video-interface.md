# 接口用错了 —— 2026-09-11

一整天在 image 接口里加证据(8→16→32 帧、运动曲线、差分图、裁剪放大),六轮全部不动。
换成模型自带的 video 接口,第一次跑就是质变。

## 为什么 image 接口加不动

gemma-4 的 `processor_config.json`:

```
image_processor:  max_soft_tokens 280   ← 整张图共享,无论塞多少帧
video_processor:  max_soft_tokens 70 × num_frames 32 = 2240  ← 每帧独占
```

池化单元 48px。所以:

| 版式 | 每帧有效分辨率 |
|---|---|
| 8 列条带 3242×456 | 264px |
| 2×2 拼 1030×1030 | 384px |
| 1×2 并排 1536×768 | 528px |
| **video 32 帧** | **约 400px × 32 帧** |

**总视觉预算差 8 倍。** 而且 video 是唯一携带**速率**的通道——运动质量主要就是速率,
抽样恰恰是毁掉速率的那一步。这解释了清单模式里"卡顿/打滑/速度/幅度"四项在 1220 条
上报出率为 **0%**:证据里根本没有答案。

## 结果

```
                        ladder(166对)   upset(689对)   顺序翻转
容量/档位先验             76.7%            0%            —
CV 12 维线性              55.6%          42.6%           —
逐处放大链              52.8–55.3%          —            —
抽样帧成对比较            48–58%            —          53–65%
VLM + video              82.2%          64.1%          22%
```

**顺序翻转从 53–65% 掉到 22%** —— 这是性质上的变化,多数判断终于经得起换边。
模型的理由也随之改变,开始讲"重心转移""跳跃感""僵硬瞬间"——整体运动属性,
放大的局部裁剪永远说不出这些。

## 两个靶子,两种失败模式,都通过

**ladder**(同配方只差容量,指纹受控):82.2% vs 容量先验 76.7%。
McNemar p=0.424(赢 15 输 10,n=90)——**这一项统计上不成立**,不能声称胜过先验。

**upset**(弱档赢强档,先验按构造 = 0%):**64.1%,z=+6.48,n=529**。
同一子集上平凡基线全在随机附近(永远选 A 50.9%、永远选 B 49.1%),
预测分布(a:261 b:268)与真值分布(a:269 b:260)几乎吻合,529 对全部顺序一致。

CV 模型在这里是 42.6%(低于随机,在骑先验)。**所以 video 版的判断不是指纹的另一种表达。**

## 教训

**在优化怎么用一个接口之前,先确认用的是不是对的接口。**
capability probe 已经会探图像预算(`token_capped` / `native_capped`),
下一条必须加:有没有 video 通道、它的预算是多少、每帧多少 token。
这是 plug-and-play 的 harness 必须先问、而我最后才问的问题。
